# HTTP 401/403/429: диагностика и политика доступа

## Что означает 401

Стандартный HTTP 401 сообщает об отсутствии подходящих аутентификационных данных и обычно сопровождается `WWW-Authenticate`. Сайты и WAF иногда возвращают его и на автоматические запросы. Один код ответа **не подтверждает**, что причиной стала защита от ботов или географическая блокировка.

- **401:** требуется аутентификация либо серверная политика доступа отказала клиенту; проверьте `WWW-Authenticate`.
- **403:** доступ запрещён для данного запроса; возможны права, политика сайта, WAF.
- **429:** ограничение частоты запросов; уменьшить нагрузку и согласовать окно доступа.

## Реализовано

1. Read-only HTTP-клиент фиксирует `phase` (robots/sitemap/page), статус, Content-Type, схему аутентификации (без realm), безопасные признаки CDN и хеш ответа.
2. **Никогда не сохраняет** cookies, пароли, Authorization-заголовок, raw WWW-Authenticate, тело страницы отказа либо сырые заголовки с токенами.
3. Ответы 401/403/429 на HTML страницах классифицируются как `blocked_http` / `rate_limited`, если страницы не получены. Такие отчёты имеют `pages_scanned=0` и `findings=[]`.
4. Частично доступный сайт получает статус `completed_sample_with_restrictions` и отдельную HTTP-диагностику.
5. Сетевая недоступность `DNS_TEMPORARY` остаётся отдельным `blocked_network`, не смешивается с HTTP.
6. Браузерный режим `--browser` выполняется только по явному разрешению владельца; отдельная проверка JS-рендеринга, а не обход 401.
7. API `/scan` по умолчанию отключён. Для private staging нужны `AUDIT_TOKEN` (32+ символа) и точные `AUDIT_ALLOWED_HOSTS`. Не публиковать API без отдельной egress-защиты.

## Как проверить, что произошло

- Если `auth_schemes` содержит `basic`/`bearer`, запросите официальный доступ или тестовые учётные данные владельца.
- Если отмечен `server_hint=cloudflare` или `challenge_indicators`, это **возможная** антибот-проверка, а не подтверждённая причина отказа.
- Если есть 429, не повторяйте запросы немедленно.
- Если 401/403 повторяются, согласуйте с владельцем staging environment, IP allowlisting или подписанные тестовые сессии; не использовать подмену клиента, CAPTCHA-solving, ротацию прокси или обход антибот-ограничений.
- Проверка sitemap и robots.txt полезна для технического контекста, но не заменяет аудит HTML страниц.
- Поисковые боты Google/Yandex/OAI могут иметь иные условия доступа; отказ нашему краулеру **не доказывает** плохую индексируемость.

## Ограничения безопасности

Фильтрация DNS до HTTP-запроса не исключает DNS rebinding. Внешнему публичному продукту нужна egress firewall с проверкой фактического IP подключения, блокировкой частных/metadata адресов, контролем редиректов, ограничениями параллелизма и квотами. Доступ браузера к произвольным URL не включать в общий API.
