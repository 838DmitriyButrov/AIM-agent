# Почему возникает DNS error — диагностика v0.2.1

## Установленная причина в текущей среде

На 22.11.2026 вызов `socket.getaddrinfo()` не работает для `lenta.com`, `metro-cc.ru`, `www.auchan.ru` **и** `example.com` (`EAI_AGAIN: Temporary failure in name resolution`). Дополнительно прямые попытки TCP-подключения к публичным адресам завершились `ConnectionRefusedError`.

Следовательно, отсутствие результата связано с политикой сетевого доступа текущего раннера (или его инфраструктурой), **а не с доказанной неисправностью DNS у целевых сайтов**. Из кода Python нельзя надежно открыть сетевой доступ там, где администратор среды его запретил.

## Что изменено

- `DNS_TEMPORARY` теперь отдельно от `DNS_NOT_FOUND` и `UnsafeTarget`.
- При отказе DNS на начальной валидации возвращается структурированный отчёт `coverage.scan_status=blocked_network` с нулём страниц и **нулём юридических/SEO-выводов**. CLI сохраняет JSON/Markdown и завершается с кодом `2`.
- `siteaudit doctor [URL]` проверяет DNS URL и отдельно *только TCP* до фиксированного публичного адреса 1.1.1.1:443 (без HTTP-запросов и без обхода ограничений).
- При блокировке сети выводятся диагностические сообщения, а не обвинения в нарушениях сайта.
- Для API код `503` сопровождается структурированным отчётом при блокировке начальной DNS-валидации.

## Проверка

```bash
siteaudit doctor https://lenta.com/
siteaudit doctor https://metro-cc.ru/ --json
siteaudit scan https://lenta.com/ --max-pages 5 --out reports/lenta
```

Если DNS исправен, но TCP-проба заблокирована, это **не** гарантирует, что сайт недоступен: корпоративная сеть может разрешать веб-доступ только через прокси. В текущей версии `httpx` запускается с `trust_env=False` намеренно: переключение на произвольные переменные proxy без контроля создало бы риск SSRF.

## Как действительно вернуть сетевой аудит

1. Запускать код на компьютере или сервере с разрешёнными исходящими запросами HTTPS и исправным DNS. В корпоративной сети попросить администратора выдать настройки DNS и разрешённый egress.
2. Для публичного API использовать **изолированный** worker с принудительным egress-фильтром и блокировкой внутренних IP/metadata-сервисов на сетевом уровне. Простая `socket.getaddrinfo`-проверка не защищает от DNS rebinding.
3. Не подменять IP целевых сайтов вслепую, не отключать `validate_public_url`, не использовать неизвестные DoH-/proxy-«обходы».
4. После изменения сетевых условий снова запустить `siteaudit doctor`; затем повторить аудиты. Не пытаться интерпретировать старые нулевые отчёты как «нарушений не найдено».

## Что не исправлено в этой версии

- У этой sandbox-среды по-прежнему нет прямого выхода в интернет: новая логика **точно объясняет и обрабатывает** блокировку, но не снимает её.
- Нужны живые браузерные тесты на стенде с сетью и разрешение на аудит, чтобы подтвердить работоспособность полного обхода.
- Команда `doctor` проверяет только прямое TCP-подключение к тестовому адресу, не общую доступность всех сайтов и не корпоративные прокси.
