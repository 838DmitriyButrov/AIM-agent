## Что изменилось относительно v0.2.1

- При HTTP 401 нет фиктивной «проблемы с SEO» (`GEO-CRAWL`) или юридической записи `NO-DATA`. Вместо этого отчёт фиксирует **ограничение доступа** и `findings=[]`.
- Добавлены поля `status_code`, `phase`, `content_type`, `auth_schemes`, `server_hint`, `response_body_bytes`, `body_sha256` и классифицированные признаки challenge. Тело ответа, cookies и токены не сохраняются.
- На главных «Ленты» и «Ашана» зафиксированы **одинаковые HTTP-ответы 401**: Content-Type `text/html`, размер 265 байт, SHA-256 `d345b3c04d0fcf410b83391892338e6c12b2e14bcfed019b1fb7aa43fedde5ed`. Нет `WWW-Authenticate`-схемы, нет `cf-ray`, не обнаружены известные challenge-маркеры. Это может указывать на общий блокирующий слой, но не доказывает конкретный WAF, геоблокировку или требование логина.
- МЕТРО: три страницы, 9 записей из базового LEGAL+GEO; одна про отсутствие H1 в статическом HTML, остальные в основном `not_tested`. Это не юридические нарушения и не подтверждение отсутствия H1 после JavaScript.

## Рекомендация

1. Использовать HTTP diagnostics и статус `blocked_http` как штатный результат ограниченного аудита, а не пробовать обходить защиту.
2. Для сайта, которым владеет заказчик, согласовать staging, IP allowlisting или официальную тестовую авторизацию; проверить на разрешённом окружении DOM после JS через `--browser`.
3. Для закрытых сайтов проводить проверку robots/sitemap и официальных данных Search Console/Вебмастера отдельно. Отсутствие HTML означает отсутствие полноценного LEGAL/SEO-аудита.
4. Публичный API не раскрывать до egress firewall против SSRF и соответствующих квот.
